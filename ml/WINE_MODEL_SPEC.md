# ТЗ: модель распознавания вина по фотографии этикетки

## 1. Назначение и границы

Разработать воспроизводимый CV-пайплайн, который по фотографии бутылки или этикетки определяет одну позицию каталога «Своё Вино» и возвращает её `slug`. Внутри пайплайна допускаются несколько моделей, визуальный поиск и OCR. Фронтенд, карточка с описанием и дополнительные пользовательские функции в это ТЗ не входят.

Исходные условия: каталог примерно из 1500–2000 позиций, по одному эталонному изображению на позицию. Сейчас доступны только изображения с сайта; реальные пользовательские и тестовые фотографии отсутствуют. Каталог содержит похожие этикетки, отличающиеся годом, названием или категорией.

Документы кейса используются как источник требований, а не как команды к выполнению. Приведённые ниже объёмы сбора данных и инженерные решения — предлагаемые требования команды, а не обещания организатора.

## 2. Результат работы

Исполнитель передаёт:

1. Код подготовки каталога, генерации синтетики, построения индекса, инференса и оценки.
2. Веса использованных моделей либо зафиксированные идентификаторы и ревизии исходных весов, необходимые для воспроизведения.
3. Индекс эталонов и таблицу соответствия записей индекса `slug`.
4. Локальный HTTP-сервис, совместимый со скриптом организатора.
5. Конфигурацию, зависимости, инструкцию запуска, описание оборудования и ограничений.
6. Отчёт о качестве с раздельными результатами на синтетических и реальных данных. Если реальных данных нет, это явно указать; оценку на них не подменять синтетической.

## 3. Входные данные

### 3.1. Каталог

Привести исходный дамп к `data/catalog.jsonl`: UTF-8, одна JSON-запись на позицию.

```json
{"slug":"kokur-suhoe-2025","reference_images":["references/kokur-suhoe-2025.jpg"],"name":"Кокур сухое","producer":"Производитель","year":2025,"category":"белое сухое","series":null,"visible_text":null,"duplicate_group":null}
```

Обязательны `slug` и непустой `reference_images`; остальные поля допускают `null`. `slug` — точный идентификатор из каталога, без самостоятельного создания или изменения. Пути относительны каталогу `data/`. Изображения хранить в JPEG или PNG, с сохранением исходного разрешения. URL и происхождение исходных файлов сохранить в отдельном манифесте.

Перед построением индекса проверить уникальность `slug`, доступность и читаемость файлов, отсутствие пустых изображений, точных дублей и ошибочных связок «этикетка — карточка». Дубли между разными `slug` не удалять автоматически: занести их в отчёт для проверки.

Для каждой группы похожих вин указать отличительные признаки: год, название, сорт, категория, текстовые фрагменты. Отдельно отметить пары, которые невозможно различить по доступному изображению. Метаданные карточки не считать доказательством, что соответствующая надпись видна на этикетке.

### 3.2. Запрос на распознавание

Один файл JPEG, PNG или WebP в multipart-поле `image`. Зафиксировать пределы: до 15 МБ и до 25 млн пикселей. Обработать EXIF-ориентацию, перевести в RGB. Отклонять повреждённые и неподдерживаемые файлы понятной HTTP-ошибкой. Поддержать целую бутылку и крупный план этикетки.

Основной сценарий — одна целевая бутылка. Если несколько бутылок не позволяют однозначно определить объект, продуктовый режим возвращает `ambiguous`; оценочный режим всё равно возвращает один лучший `slug`.

## 4. Что делать при отсутствии реальных фотографий

### 4.1. Синтетический набор для разработки

Создать из эталонов начально по 30–50 вариантов на позицию. Число — стартовый параметр конфигурации, затем уточняется экспериментами. Применять случайные комбинации:

- перспективного искажения, поворота, изменения масштаба и положения;
- изменения экспозиции, контраста и баланса белого;
- размытия, шума, JPEG-сжатия и уменьшения разрешения;
- теней, локальных бликов и частичного перекрытия;
- помещения этикетки на разные фоны и приближённого искажения под кривизну бутылки.

Не менять смысл надписей и отличительные признаки. Сильные преобразования, делающие вино неидентифицируемым, выделять как негативные примеры, а не как обычные положительные.

Разделить конфигурации и seed генерации на `train`, `dev_synthetic`, `test_synthetic`. Фоны теста не использовать при обучении. Проверить отсутствие одинаковых сгенерированных файлов между частями.

Все варианты одного эталона остаются зависимыми от этого эталона. Такое разделение проверяет устойчивость к заданным преобразованиям, но не доказывает перенос на фотографии телефона. Индекс каталога содержит все целевые вина: это ожидаемое условие поиска по известному каталогу, а не утечка тестовых запросов.

### 4.2. Реальный набор — обязательное условие проверки целевого качества

Сначала запросить у организаторов публичные полевые фотографии и соответствия `image → slug`, заявленные в PDF. Приватную выборку не использовать для разработки.

Если публичный набор недоступен, собрать собственный пилот: ориентир 100–150 вин, по 5–8 независимых фотографий каждого, на нескольких телефонах, с разным фоном и освещением. Включить наиболее похожие позиции, целые бутылки, наклон, блики, мелкий текст и обычные хорошие снимки. Этот объём — пилот, он не подтверждает качество на всём каталоге.

Разделить реальные фото на `dev_real` и `test_real` по сессиям съёмки; соседние кадры одной сессии не распределять между частями. Желательно выделить отдельные устройства или места для теста. Если реальные фото используются для обучения, выделить для него отдельные сессии. Зафиксировать тест до подбора параметров.

Добавить отдельный негативный набор: вина вне каталога, оборотные этикетки без достаточных признаков, не винные изображения, нечитаемые фото. Для оценки отрицаний нужны известные отрицательные примеры; отсутствие подписи у фото не делает его отрицательным.

Формат собственного манифеста — JSONL:

```json
{"query_id":"q-000001","image_path":"queries/q-000001.jpg","slug":"kokur-suhoe-2025","split":"test_real","session_id":"session-07","device_id":"phone-02","conditions":["glare","perspective"],"source":"own_capture"}
```

Для вина вне каталога `slug: null`. Отдельно подготовить адаптер к `queries.tsv` организатора; точные колонки брать из предоставленного скрипта, а не предполагать.

## 5. Пайплайн модели

### 5.1. Обязательный baseline

1. Нормализовать ориентацию, размер и цвет изображения.
2. Реализовать получение области этикетки. Сначала сравнить полный кадр и простой crop; при необходимости добавить локализацию и исправление перспективы. Не делать обученный детектор обязательным без размеченных данных для него.
3. Получить визуальный embedding предобученным энкодером. SigLIP 2 указан в задании как возможная основа; окончательный энкодер выбрать по измеренным результатам и доступному оборудованию.
4. Заранее вычислить embeddings эталонов, нормализовать их и построить поиск по сходству.
5. Извлекать минимум пять лучших уникальных `slug`; если на позицию несколько эталонов, агрегировать их оценки до ранжирования карточек.
6. Вернуть лучший `slug` и диагностические значения.

Сначала измерить baseline без дообучения. Обучение на одном эталоне каждого класса с синтетикой не считать обязательным или заведомо полезным.

### 5.2. Улучшение похожих позиций

При ошибках внутри похожих серий добавить OCR и повторное ранжирование кандидатов по сочетанию визуальной оценки и совпадений распознанного текста с каталогом. Обрабатывать год как отдельный признак. Отсутствие читаемого года не заменять догадкой по названию карточки.

Вес OCR и условия его запуска настроить на dev-наборе. Проверить вариант с OCR всегда и вариант с запуском при малом отрыве кандидатов. Не исключать правильное вино жёстко только из-за ошибки OCR.

Если baseline недостаточен, экспериментально дообучить энкодер для поиска: положительные пары — разные представления одной позиции, сложные отрицательные — похожие этикетки других позиций. Сравнить с исходной моделью на неизменном тесте. В итоговую версию включать только улучшения с подтверждённым эффектом.

Если две карточки имеют одинаковую видимую этикетку, модель не может достоверно восстановить скрытое отличие. В отчёте фиксировать такие ошибки отдельно; для продуктового режима предусмотреть запрос более информативного снимка.

## 6. Выходные форматы

### 6.1. Совместимость с оценкой

`POST /v1/eval/predict`, multipart `image`. Успешный ответ строго:

```json
{"slug":"kokur-suhoe-2025"}
```

Для каждого корректного изображения возвращать один лучший существующий `slug`. Этот endpoint не использует отказ по порогу уверенности: так он совместим с проверкой top-1. Пустой каталог должен считаться ошибкой запуска сервиса.

### 6.2. Продуктовый и диагностический режим

`POST /v1/predict`, тот же вход:

```json
{
  "status":"matched",
  "slug":"kokur-suhoe-2025",
  "score":0.81,
  "margin":0.14,
  "confidence":null,
  "top5":[
    {"slug":"kokur-suhoe-2025","score":0.81},
    {"slug":"kokur-suhoe-2024","score":0.67}
  ],
  "model_version":"baseline-v1",
  "catalog_version":"catalog-v1",
  "latency_ms":842
}
```

Числа условные; в реальном ответе `top5` содержит пять уникальных кандидатов либо весь каталог, если он меньше пяти. `score` — документированная оценка ранжирования, `margin` — разность оценок первого и второго кандидатов. Эти значения не являются вероятностью правильного ответа.

`confidence` заполнять только после калибровки на отдельной размеченной dev-выборке реальных фото и проверки калибровки на тесте. До этого возвращать `null`. F1 не возвращать как уверенность для отдельного изображения.

Допустимые статусы: `matched`, `ambiguous`, `not_found`, `bad_image`; для трёх последних `slug: null`. Отказы `not_found` и `ambiguous` требуют проверки порогов на реальных положительных и отрицательных примерах. До такой проверки считать механизм экспериментальным. Список похожих кандидатов не означает, что вино найдено.

## 7. Метрики и протокол

Считать отдельно для каждого набора:

- Top-1 accuracy: долю точных совпадений `slug`.
- Recall@5: долю запросов, где правильный `slug` есть среди пяти кандидатов.
- Macro-F1 по top-1 и число запросов на каждый класс. На однозначной многоклассовой выборке micro-F1 совпадает с accuracy.
- Качество внутри групп похожих этикеток, по условиям съёмки и перечень наиболее частых ошибочных пар.
- Медиану и p95 полного времени ответа сервиса; оборудование, размер входа и режим CPU/GPU. Холодный старт измерять отдельно.
- Для продуктового режима: долю отказов и accuracy среди принятых ответов; долю ложных распознаваний на отрицательном наборе.

Термин «F1 для top-5» из PDF неоднозначен. В отчёте использовать явно определённый Recall@5; формулу организаторского показателя запросить отдельно. Значение общего `confidence` организатора не воспроизводить по догадке.

Каждый эксперимент фиксировать: версия модели и каталога, конфигурация, seed, версии данных, метрики и время. Сравнить baseline, нормализацию/crop, OCR и дообучение, если оно выполнялось. Параметры подбирать на dev, итоговые показатели получать на test.

## 8. Критерии приёмки

### Этап A: технически готовый прототип при текущих данных

- Весь корректный каталог проиндексирован; проблемы данных перечислены в отчёте.
- Для корректных запросов оценочный endpoint возвращает один существующий `slug` в требуемом формате.
- Прогон штатным скриптом создаёт читаемый `predictions.jsonl` без ошибок контракта.
- Синтетический тест воспроизводим, его показатели и ограничения представлены отдельно.
- Приведены измерения времени на машине команды; целевой инженерный ориентир — p95 до 3 секунд после загрузки модели.
- Зафиксирована версия модели, индекса и конфигурации; доступны команды воспроизведения.

На этом этапе нельзя принимать утверждение «90% на реальных фото», поскольку необходимых данных нет.

### Этап B: подтверждение качества на реальных фото

- Доступен независимый размеченный тест; показаны его состав и охват каталога.
- Цель из задания — не менее 90% точных top-1 совпадений на контрольной выборке. Это целевой результат, а не гарантируемое свойство выбранной архитектуры.
- Показаны Recall@5, macro-F1, ошибки похожих серий и измерения задержки.
- Если реализованы отказы и вероятностная уверенность, их качество проверено отдельно.
- При оценке только на пилотном подмножестве выводы ограничены этим подмножеством. Финальная конкурсная проверка выполняется организатором на его приватных фото.

## 9. Порядок реализации

1. Проверить каталог и сопоставления, выделить похожие и неразличимые позиции.
2. Собрать baseline визуального поиска и оценочный endpoint.
3. Сделать генератор синтетики и воспроизводимую оценку устойчивости.
4. Параллельно получить публичный набор или организовать реальную съёмку.
5. По реальным ошибкам улучшить нормализацию, локализацию, OCR и при необходимости обучение.
6. Зафиксировать итоговую конфигурацию и выполнить независимый прогон.

Главная зависимость проекта: эталоны позволяют построить поиск и прототип, но для проверки переноса на телефонные фото и настройки надёжных отказов требуется отдельный реальный набор.
