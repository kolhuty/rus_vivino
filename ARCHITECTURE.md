# Архитектура сервиса распознавания российских вин

## 1. Назначение системы

Сервис распознаёт российское вино по фотографии бутылки или этикетки и возвращает
карточку соответствующей позиции каталога «Своё Вино». Основной сценарий рассчитан
на мобильный браузер: пользователь делает снимок камерой телефона либо выбирает
изображение из галереи.

Текущая версия использует визуальный поиск на основе SigLIP 2. OCR, обучение модели
на данных конкурса и внешние API в основном поисковом pipeline не используются.

## 2. Компоненты

Система разделена на три независимо собираемых сервиса.

```text
Мобильный или настольный браузер
              |
              | HTTP, multipart/form-data и JSON
              v
Frontend: React + Nginx, порт 80
              |
              | /api/*
              v
Backend: Flask + Gunicorn, порт 8000
       |                         |
       | HTTP                    | catalog.jsonl и изображения
       v                         v
ML service: FastAPI, порт 8001   Локальный каталог
       |
       | SigLIP 2 + cosine similarity
       v
artifacts/index.npz
```

### Frontend

Код находится в `frontend/`.

- Получает изображение с камеры или из галереи.
- Отправляет его в `POST /api/v1/recognize`.
- Показывает одну основную карточку и до четырёх похожих позиций.
- Предоставляет переход на карточку вина портала «Своё Вино».
- Содержит точку входа для дополнительной функции «Цифровой сомелье».

Frontend не выполняет распознавание и не принимает решение о найденном вине.

### Backend

Код находится в `backend/`.

- Предоставляет публичное API приложения.
- Передаёт изображение в ML-сервис без изменения содержимого.
- Обогащает результаты поиска сведениями из `data/catalog.jsonl`.
- Формирует JSON основной карточки и похожих вин.
- Отдаёт локально сохранённые изображения каталога.
- Предоставляет отдельный endpoint с минимальным контрактом для оценочного скрипта.

Backend не извлекает визуальные признаки и не выполняет ранжирование кандидатов.

### ML-сервис

Код находится в `ml/wine_recognition/`.

- Проверяет и нормализует входное изображение.
- При необходимости локализует центральную бутылку и область этикетки.
- Извлекает нормализованные визуальные признаки моделью SigLIP 2.
- Ищет ближайшие позиции в заранее построенном индексе.
- Возвращает лучший `slug` либо расширенный диагностический результат.

ML-сервис не обращается к каталогу карточек во время запроса: соответствие векторов
и `slug` хранится непосредственно в индексе.

## 3. Pipeline распознавания

### Шаг 1. Получение изображения

Frontend отправляет JPEG или PNG в multipart-поле `image`. Допускается файл размером
до 15 МиБ и изображение до 25 миллионов пикселей.

Для скрипта организатора запрос поступает в `POST /api/v1/scan`. Для интерфейса
приложения используется `POST /api/v1/recognize`.

### Шаг 2. Валидация и нормализация

Модуль `ml/wine_recognition/images.py`:

1. проверяет размер файла;
2. декодирует JPEG или PNG через Pillow;
3. отклоняет повреждённые и неподдерживаемые изображения;
4. применяет EXIF-ориентацию;
5. проверяет количество пикселей;
6. переводит изображение в RGB.

Геометрическая коррекция перспективы, устранение бликов и OCR в текущей версии
не применяются.

### Шаг 3. Локализация бутылки и этикетки

Локализатор включается переменной `WINE_LOCALIZER` и по умолчанию активен.

1. YOLOS Small находит объекты класса `bottle`.
2. Слабые и пересекающиеся детекции фильтруются.
3. Если найдено несколько бутылок, выбирается бутылка, ближайшая к центру кадра.
4. Внутри бутылки эвристически выбирается область с высокой детализацией,
   соответствующая этикетке.
5. Для поиска используются два представления: вся найденная бутылка и этикетка.

Если бутылка не обнаружена, pipeline использует полный исходный кадр. Поэтому
отсутствие детекции не приводит к ошибке запроса.

### Шаг 4. Извлечение признаков

Энкодер `SiglipEncoder` использует модель
`google/siglip2-base-patch16-224`. Ревизия модели сохраняется в метаданных индекса.

Изображения преобразуются штатным `AutoImageProcessor`, после чего модель получает
визуальные признаки методом `get_image_features`. Векторы приводятся к `float32` и
нормализуются по L2-норме.

Доступно выполнение на CPU и CUDA. При `WINE_DEVICE=auto` CUDA выбирается только
при её наличии.

### Шаг 5. Поиск по индексу

Индекс `artifacts/index.npz` содержит:

- нормализованные векторы эталонных изображений;
- точные `slug` каталога;
- идентификатор и ревизию модели;
- версию каталога;
- версию ML-pipeline.

Для каждого запроса вычисляется cosine similarity со всеми эталонными векторами.
Если у позиции несколько эталонов или у запроса несколько представлений, берётся
максимальная similarity для каждого `slug`. Кандидаты сортируются по убыванию
score; при равенстве используется `slug`, что делает результат детерминированным.

Текущий размер каталога позволяет выполнять полный матричный поиск без отдельной
векторной СУБД. Индекс загружается в память один раз при старте ML-сервиса.

### Шаг 6. Формирование ответа

Оценочный endpoint возвращает строго один объект:

```json
{"slug":"wine-slug"}
```

Диагностический endpoint возвращает:

```json
{
  "status": "matched",
  "slug": "wine-slug",
  "score": 0.89,
  "margin": 0.14,
  "confidence": null,
  "top5": [
    {"slug": "wine-slug", "score": 0.89}
  ],
  "model_version": "siglip2-baseline-v1",
  "catalog_version": "catalog-v1",
  "latency_ms": 1035
}
```

`score` является cosine similarity, а `margin` — разностью score первого и второго
кандидатов. Это не калиброванная вероятность. Поле `confidence` остаётся `null`, пока
порог и калибровка не будут рассчитаны на отдельной размеченной выборке реальных фото.

Backend сопоставляет полученные `slug` с каталогом и возвращает frontend основную
карточку в `main`, а остальных кандидатов — в `others`.

## 4. API-контракты

### `POST /api/v1/scan`

Публичный оценочный endpoint backend. Принимает multipart-поле `image` и при
успешном распознавании возвращает только:

```json
{"slug":"wine-slug"}
```

### `POST /api/v1/recognize`

Продуктовый endpoint frontend. Возвращает карточку, похожие позиции, диагностические
поля модели и время ML-инференса.

### `GET /api/v1/wines/{slug}`

Возвращает карточку позиции локального каталога либо HTTP 404.

### `GET /api/v1/health`

Проверяет доступность backend, размер каталога и соединение с ML-сервисом.

### Внутренние endpoints ML

- `POST /v1/eval/predict` — минимальный ответ с `slug`.
- `POST /v1/predict` — расширенный top-5 и диагностика.

ML-сервис и backend не публикуются наружу в Docker Compose; снаружи доступен только
Nginx frontend.

## 5. Подготовка каталога и индекса

Исходный каталог преобразуется скриптом `ml/scripts/prepare_catalog.py` в
`data/catalog.jsonl`. Каждая запись содержит уникальный `slug` и непустой список
`reference_images`.

При подготовке:

- проверяется однозначность сопоставления изображения и позиции;
- повторяющиеся `slug` отклоняются;
- неоднозначности и дубли записываются в `data/catalog_report.jsonl`;
- происхождение локальных изображений сохраняется в `data/sources.jsonl`.

Индекс строится отдельной командой до запуска сервиса:

```bash
PYTHONPATH=ml python -m wine_recognition build-index --device cpu
```

В PowerShell эквивалентная команда начинается с `$env:PYTHONPATH="ml"`.

Изменение каталога или модели требует полного перестроения `artifacts/index.npz`.
Скорость переиндексации не входит в критический runtime-path пользовательского
запроса.

## 6. Оценка качества

Скрипт `scripts/evaluate.py` последовательно отправляет изображения в сервис и
сохраняет результаты в `reports/`.

Рассчитываются:

- Top-1 accuracy — доля точных совпадений `slug`;
- macro-F1 по результату top-1;
- Recall@5 — доля запросов, где правильный `slug` присутствует в первой пятёрке;
- median и p95 клиентского времени ответа;
- median и p95 времени ML-инференса;
- качество по условиям съёмки;
- наиболее частые пары ошибок.

Термин «F1 для top-5» неоднозначен для задачи многоклассового поиска, поэтому в
отчёте он представлен явно определённым Recall@5. Значения качества должны
публиковаться только после прогона на размеченных полевых фотографиях; результаты
на эталонных изображениях не заменяют такую оценку.

## 7. Конкурентность и производительность

Модель и индекс загружаются один раз при старте процесса. Внутри `WineRecognizer`
инференс защищён блокировкой, чтобы параллельные запросы не обращались к одному
экземпляру модели одновременно. ML-сервис запускается с одним worker, что также
предотвращает создание нескольких копий модели в памяти.

Backend может обслуживать несколько HTTP-запросов, но фактическая пропускная
способность распознавания ограничена последовательным ML-инференсом. Для масштаба
локальной демонстрации это осознанный компромисс в пользу предсказуемого потребления
памяти.

Время в поле `latency_ms` измеряет обработку уже загруженной моделью и не включает
старт контейнера или первоначальное скачивание весов.

## 8. Развёртывание

`docker-compose.yml` запускает:

- `frontend` — Nginx со статической React-сборкой;
- `backend` — Flask под Gunicorn;
- `ml` — FastAPI под Uvicorn;
- volume `huggingface-cache` для кеша весов моделей.

Каталог, изображения и индекс монтируются в контейнеры в режиме read-only. При
первом запуске ML-контейнеру требуется доступ к Hugging Face для получения весов.
Следующие запуски используют Docker volume с кешем.

Основные переменные окружения:

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `APP_PORT` | Публичный порт Nginx | `80` |
| `ML_TIMEOUT` | Таймаут backend при обращении к ML | `120` секунд |
| `WINE_DEVICE` | `cpu`, `cuda` или `auto` | `cpu` в Compose |
| `WINE_LOCALIZER` | Включение локализации бутылки | `1` |
| `WINE_INDEX` | Путь к индексу внутри ML-контейнера | `/artifacts/index.npz` |

## 9. Обработка ошибок

- Отсутствие multipart-поля `image` приводит к HTTP 400.
- Повреждённый файл и неподдерживаемый формат приводят к HTTP 400.
- Превышение 15 МиБ приводит к HTTP 413.
- Недоступность ML-сервиса приводит к HTTP 503 на backend.
- Пустой или повреждённый индекс считается ошибкой запуска ML-сервиса.
- Отсутствующий `slug` в каталоге приводит к HTTP 404 при прямом запросе карточки.

## 10. Известные ограничения

1. Поисковый endpoint всегда выбирает ближайший `slug`. Откалиброванного отказа
   `not_found` для вина вне каталога пока нет.
2. `score` и `margin` не являются вероятностью правильного ответа.
3. OCR и специальное различение near-duplicate этикеток по году или категории пока
   отсутствуют.
4. Качество зависит от полноты и корректности единственного эталонного изображения.
5. Поля карточек ограничены сведениями, реально присутствующими в подготовленном
   `catalog.jsonl`.
6. «Цифровой сомелье» пока является точкой расширения интерфейса, а не законченной
   функцией.
7. Горизонтальное масштабирование и распределённый векторный индекс не реализованы,
   поскольку они не требуются для локальной демонстрации каталога текущего размера.

## 11. Границы дальнейшего развития

Без изменения публичного API архитектура допускает:

- улучшение нормализации перспективы и бликов;
- добавление OCR как второго сигнала для near-duplicates;
- калибровку `not_found` по score, margin и отрицательной выборке;
- добавление нескольких эталонных изображений на один `slug`;
- реализацию полезной функции после поиска;
- замену полного матричного поиска на векторную БД при существенном росте каталога.

Каждое изменение поискового pipeline должно сопровождаться новым `model_version`,
перестроением индекса и сравнительным прогоном на неизменной оценочной выборке.
